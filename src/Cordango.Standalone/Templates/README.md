## Running it

```
docker compose up --build
```

That is the whole thing — no `.env` to write first, no migration to run, no password to go and look
up. Open <http://localhost:8080> and the first screen asks you to **create the administrator
account**.

That form is reachable only while this application has no administrator at all. From the moment one
exists it refuses everybody, and no setting reopens it. The window is the seconds between the
database coming up and you opening the page — the same one every self-hosted application has. If the
first request to arrive will not be yours, set `ADMIN_EMAIL` and `ADMIN_PASSWORD` in `.env` (copy
`.env.example`) instead: the account is then created at startup and the setup screen never appears.

There is deliberately no default password. A fixed one would mean every application this toolchain
produces ships with the same credentials, and a generated one can only be delivered by printing it to
a log — which is not an answer for anybody who arrived through a browser.

`DB_PASSWORD` has a local-only default so the above works with nothing configured. That is safe here
and only here: the database service publishes no port, so nothing outside the compose network can
reach it. Set a real one before this runs anywhere but your machine.

There is no migration step. The application creates and updates its own schema on the way up, from
the migration files in `api/Migrations/` — which you can read before you run it, and edit afterwards.

## Running it without Docker

```
docker compose up -d db          # Postgres, and nothing else

cd api && dotnet run             # schema, demo data, API and the built front end

cd web && npm install && npm run dev    # only if you are changing the front end
```

Still no migration step: `dotnet run` is enough. `npm run dev` proxies `/api` to the back end so the
two behave as one origin, which is how they are served in production — you only need it while you
are editing components.

## Regenerating

Running the generator again over the same output directory replaces the files it wrote last time and
leaves everything else alone. `cordango.build.json` lists exactly which files those are, so there is
never a guess about what is safe to edit.

Files marked *generated* above will be overwritten. To change what they contain, change the App
Definition. To add behaviour, add files of your own beside them — a hook registered in its own file,
a controller with its own route, a page the router picks up. That is the intended way to extend a
generated application, and it survives every rebuild.

## Changing the schema

After generation this is a normal EF Core project:

```
cd api
dotnet ef migrations add WhateverYouChanged
```

The application applies pending migrations at startup.

## Who may do what

Permissions come from the definition's roles and are compiled into `api/Security/AppRoles.cs`: which
entities a role may read, create, change and delete, which fields it may see or set, and which
commands it may run. The rules are enforced on every route, and a field a role cannot read never
appears in a response — not in the record, and not in a message rendered from it.

Two things are decided outside the definition, because the definition has nothing to say about them:

- **Signing in** is stock ASP.NET Core Identity with a cookie. Swap it for single sign-on by
  changing `api/Identity/AppIdentity.cs`.
- **The `Administrator` role** bypasses definition roles entirely. It is an ASP.NET role rather than
  a definition role, so reading the definition never turns up a role that grants more than it says.

## What is not generated yet

`cordango.build.json` lists it exactly, under `unsupportedCapabilities`, and the section above
appears in this README when there is anything to report. As of this build the generator does not yet
emit **workflows**, **computed fields and rollups**, **command guards**, or the **email and webhook**
effects. In-app **notifications** are generated and do work.

A build that needs any of those refuses unless you pass `--allow-incomplete`, so an application that
was built completely is one you can trust to be complete.

## Security worth knowing about

- Every state-changing request requires an antiforgery token, enforced globally rather than per
  controller — including on a controller you add later without reading this.
- The front-end client in `web/src/api.js` attaches the token automatically. Anything that talks to
  the API should go through it.
- Uploaded files are addressed by the hash of their contents, so a reference cannot be guessed or
  enumerated. Any signed-in caller who *has* a reference can fetch the file behind it, including one
  attached to a record their role cannot read.
- The demo dataset is loaded only into empty tables, and only when `SEED` is set. It cannot
  overwrite real records, but turn it off for a real deployment anyway.
- Error responses are `{"code": "...", "error": "..."}`. The code is stable and safe to switch on;
  the message is translated. Exception detail is logged, never sent.
